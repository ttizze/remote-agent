# 会話管理と同期の T3 Code 準拠計画

会話管理、履歴、実行、一覧を T3 Code の方式へ統一する。保存済みの会話を読むたびに provider の履歴と合成する経路と、置き換えた旧実装を取り除く。

この文書は未完了の実装・レビュー・検証を進めるための計画である。完了した作業の記録は残さず、全体の完了後に削除する。

## 前提と範囲

- 利用者が明示的に変更を指定した部分以外は、T3 Code の動作を基準にする。問題を見つけたら、対応する T3 の実装、呼び出し元、成立条件を先に確認する。
- 必要な過去の会話は provider の履歴から新しい DB へ初回取り込みする。DB とキャッシュは新規に開始する。
- 一度取り込んだ会話の履歴は再取り込みしない。プロジェクトを再取り込みしても、取り込み済みの会話へ Host 外で増えた本文を追記しない。
- 初回取り込み後の正本は Host の SQLite DB とする。Bex の実行中に受けた provider イベントは DB へ反映する。
- 既存の公開会話識別子は維持する。新規会話はクライアントが発行した provider 非依存 UUID、外部会話は従来の `SessionRef { provider, id }` で参照する。選択中の provider を公開 ID から推定しない。
- Bex のネイティブ UI、DeepSeek 接続、未登録フォルダからの利用など、既存の利用側も確認する。T3 と異なる接続や表示が必要な場合は、その制約を所有するコードの近くに置く。
- この作業では main への統合・push・配布を行わない。稼働中 Host、`/Applications/Bex.app`、iPhone のインストール済みアプリ、保存済み旧版 `/Users/tt/Library/Application Support/Bex iPhone Host/d49e188142b4/Bex.app` を停止・更新・再起動・再インストール・削除しない。他セッションの差分と stash を保持し、追加エージェントは起動しない。

## 設計

### 保存と実行

- T3 の Thread、Run、RunAttempt、ExecutionNode、TurnItem、ProviderSession／Thread／Turn、RuntimeRequest、ContextTransfer／Handoff の役割に揃える。
- キューと準備中の入力も Run の状態として管理する。キュー内の入力と会話本文への表示は T3 の規則に従い、二重表示しない。
- 現在の投影、連番付きイベント、コマンドの受付結果、副作用を記録する outbox を一つの SQLite で所有する。採用する変更と副作用は受付結果と同じトランザクションで保存し、コミット後に配信・実行する。
- 状態の判断は必要な値を受け取る純粋な処理で行う。DB、SDK 接続、コールバック、出力バッファの更新・解放は各資源の所有者が行う。
- 同じ操作 ID の再送は保存済みの受付結果を返す。provider への送信が成功したか不明な場合、元の入力を自動再送しない。
- 副作用は永続化した状態・所有権・実行順を使って進める。古い worker や接続からの結果が現在の試行を更新しないようにする。安全な再試行と、二度実行してはいけない native 操作を T3 の規則で区別する。
- T3 が持つ型や表を用途なしに複製しない。表示や実行に不要な状態、二重に保存する本文、判断を転送するだけの層は残さない。

### 初回取り込みと読み取り

- 明示したプロジェクトの取り込みで、対象 provider の外部会話を取り込む。T3 と同じくテキスト・推論を取り込み、過去の SDK 実行を Bex の Run として捏造しない。
- 取り込みの完了印と本文を一緒に確定する。途中の読み取り失敗では完了印を残さず、次回の明示操作で初回取り込みをやり直せる。
- 既に取り込み済み、または Bex の Run がある会話の履歴は再取り込みしない。別の Bex 会話が所有する native resource を別会話として取り込まない。
- 取り込み済みの通常の表示、過去ページ、詳細、検索、履歴引き継ぎは新 DB から読む。provider の実行ファイルや履歴ファイルが利用できなくても、保存済みの内容を読めるようにする。
- 詳細の省略は通信・表示用の投影で行う。実行中に受け取った保存対象の詳細は所有する DB に置き、展開時に native 履歴を再読する仕組みを残さない。コマンド出力の保存上限は T3 の規則に従う。
- 検索は canonical な会話・本文とプロジェクトから行い、通常の検索に native カタログの走査・合成を持ち込まない。

### 同期とクライアント

- 会話と一覧は同じ DB のイベント連番を使い、各購読がそれぞれ受信位置を持つ。通常の再接続は T3 と同じイベント再生かスナップショットへの置き換えで扱う。
- 購読を開始してから現在状態・未受信イベントを読み、境界で重なるイベントは連番で重複適用しない。保持期間外、現在より先のカーソル、再生量の上限超過などは T3 と同じ条件でスナップショットへ切り替える。
- イベント保持は参照 T3 の一日を基準にする。受付結果の寿命と再送判定をイベント保持と混同しない。
- 過去ページと詳細は T3 と同じ別問い合わせで扱う。問い合わせ結果は会話、Host、接続・購読世代、要求したページ境界または項目の版に照らし、新しい状態を上書きさせない。
- 会話の初期表示は最新の 10 ターンを保ち、過去はページング、作業の詳細は展開時に読む。取り込み済みの会話を開く処理で全履歴を読み直さない。初回取り込みの所要時間と通常の表示時間は分けて確認する。
- クライアントの会話状態は canonical な投影とイベントの適用結果から作る。core が共通の表示判断を所有し、各 OS の UI・FFI に同じ判断を作り直さない。
- 一覧・プロジェクト・未読・通知・Live Activity も同じ canonical な状態を利用する。
- 本文の区切り送信は T3 の 400 ms／800 ms を基準にする。実行中のコマンド出力は専用の購読で流し、展開直後の末尾取得、途中参加、完了時の保存を同じ所有者で扱う。出力ごとに会話全体を DB から読み直さない。

### 分岐、provider 切替、巻き戻し

- 分岐は T3 の履歴参照と選択境界に揃える。親の表示・履歴を保ち、子の継続は独立した native resource を使う。
- provider 切替と分岐後の継続は、選択済みの履歴、native fork の能力、履歴の容量、配信済みの範囲を使って T3 と同じ方法を選ぶ。送信の受付時点で必要な引き継ぎを確定する。
- 履歴の注入結果が不明な native resource へ同じ内容を再注入しない。復旧時も元の入力を重複配送しない。
- 巻き戻しは T3 の能力判定と実際の native 操作に従う。Codex は同じ native thread の保持する head へ戻す。未対応 provider の巻き戻しは能力判定で拒否する。
- Claude は実際の assistant message ID と SDK の再開位置を使う。別種の turn ID を再開位置として渡さず、分岐から継承した履歴も境界に含める。
- native 操作の成功を確認してから、Run・Node・head と関連する checkpoint の状態を確定する。失敗・結果不明・Host の再起動を挟んだ場合も、成功したように表示せず、余計な巻き戻しや入力配送をしない。
- CheckpointScope／Checkpoint は T3 の実行完了・巻き戻しに必要な範囲で扱う。今回、ファイルシステムのスナップショットやファイル復元の製品機能は追加しない。

### 中断、要求、再起動、資源解放

- Stop の受付と provider の実際の終了を区別する。終了を確認する前に完了状態を作らず、最後の出力も保存する。
- 承認・質問への回答は canonical な RuntimeRequest を通す。画面から要求が消えた後も、回答の native 呼び出しが終わるまでは必要なコールバックを保持する。
- 中断・失敗・再起動、不確実な配送、容量待ち、バックグラウンド作業は、T3 の状態遷移・キューの扱いに揃える。古い物理会話のイベントを現在の会話・試行へ流用しない。
- 更新による再起動の継続は同じ公開会話へ一度だけ記録し、元の依頼を再送しない。実際の Host 更新は今回行わず、保存と provider 境界を通す試験で確認する。
- 完了・切断・provider 停止で不要な接続、要求ハンドル、出力バッファを資源の所有者が解放する。遅れた旧コールバックで解放済みの実行や新しい接続を復活・切断させない。

## 残作業の順序と受入条件

各段階で、先に利用者から観測できる期待値を T3 または明示された Bex の要求から定める。実装が誤っていた場合の条件・影響を考え、影響の大きい境界から確認する。

### 1 詳細と検索を DB に統一する

- `host_rpc/runtime/bodies.rs` の native 履歴への再読と、そのためだけの状態・再試行・テスト前提を削除する。
- provider イベントの受信から保存まで追い、必要な詳細が最初から DB に残るようにする。省略済み DTO を読み直すことで保存不足を隠さない。
- `host_rpc/service/titles.rs::search_list` を canonical な検索へ切り替え、利用側も更新する。会話本文を検索する条件は T3 の `ThreadSearch.ts` と照合する。

受入条件: 実際のイベントを通して保存した会話を閉じ、provider 履歴を利用不能にしても、再度開く・過去を読む・詳細を展開する・検索する操作が DB の内容を返す。保存された別会話の詳細を読むことがなく、未取り込みの native 会話が通常検索に混入しない。

### 2 巻き戻しを native 操作まで接続する

- `orchestration/rollback.rs` の判断を、Runtime の effect handler と provider adapter を通して実際の native 操作へ接続する。
- Codex の保持 head と Claude の再開位置を、T3 の呼び出し条件に従って解決する。チェックポイント、native ref、選択中 provider が食い違う場合は変更前に拒否する。
- 成功・拒否・応答喪失・再起動・キューとの競合を通し、古い fork 代替処理とその期待値を取り除く。

受入条件: Codex は同じ native thread で選択した地点から続き、Claude は実際の SDK 再開位置から続く。失敗時に表示だけが巻き戻らず、再試行でさらに過去へ戻らず、保持すべき分岐元の文脈が失われない。未対応 provider は誤った能力を公開しない。

### 3 取り込みと同期の利用側を確認する

- 初回取り込みの一回性と、明示的なプロジェクト取り込みの対象範囲を、登録済み・未登録・既所有の会話で確認する。
- 会話／一覧の購読、キャッシュ、ページ、詳細、APNS／Live Activity と各 UI の入力を追う。通常の再接続と別 Host・旧接続からの結果を区別する。
- SDK イベントと公開会話の対応を、provider 切替・サブエージェント・バックグラウンド作業も含めて確認する。

受入条件: 再取り込みで本文が追記されず、初回失敗だけが再試行できる。重複・再接続・過去ページの遅着で会話が増えたり古い状態へ戻ったりせず、入力・エラー・録音状態も上書きされない。同じ要求とキューをどのクライアントからも操作できる。

### 4 不要な実装を削除し、検証対象を揃える

- `agent-protocol/src/sync.rs` の旧 Cursor／Row／Message／Replica など、本番の利用側がない同期実装を削除する。現在利用している購読範囲とコマンド出力の責務は残す。
- 旧ストレージ・旧所有者・旧一覧・旧 DTO・旧取り込み／詳細経路の参照を、Host、core、CLI、fixture、各アプリまで追って除く。
- `scripts/t3-port-check/cases.json` の対象を、現在の要求と実際に動く検証経路に揃える。各シナリオが検証する要求を明確にし、必要なシナリオを省かずに検証する。
- 不要なコードを削除した後、影響する呼び出し元を再度読み、削除によって不要になった状態や転送も除く。この確認を不要な実装が見つからなくなるまで繰り返す。

受入条件: 通常の表示・検索・実行が旧実装を通らず、残す共通判断の所有者と利用側をソース上で説明できる。別実装を残す場合は異なる要求または資源制約がある。

### 5 最終の動作とビルドを確認する

- 重要な回帰試験は、実際の RPC、保存、worker、provider の記録イベントをつなぐ。問題が起きる部分を stub で省略した試験だけで結論を出さない。
- 再送、遅着、接続切替、Run の境界、outbox の所有権・順序、部分読み込みと再接続の組み合わせを確認する。生成試験の期待値は、同じ時点の保存済み投影や独立した契約から導く。
- 結果不明の native 書き込み、巻き戻し、要求ハンドル、古い物理会話からの通知は、想定する誤りを実際に検出できる回帰試験を置く。分岐・状態遷移は対象を限定した cargo-mutants でも確認する。
- 通常の会話を開く速さと転送量を、短い会話・長い会話・分岐した会話で比較する。取り込み済み会話の通常表示と初回取り込みを分け、実際の DB・RPC・クライアントを通す経路を測る。保護対象の稼働環境では実行しない。
- 開発・検証は `scripts/dev-env.sh` を使う。共通 Rust は設定済み builder で実行し、接続できない場合に Mac へ切り替えない。
- 変更中は対象 crate の `cargo nextest run --locked -p <crate>` と `just complexity`、全体が揃ってから `cargo check --locked --workspace --all-targets` と共通の `just unit-tests` を実行する。複雑度の閾値・除外・抑制を変えて通さない。
- Apple のビルド・Native clients CI・実機 UI は共通 Rust の結果と分けて報告する。今回、ローカルの native ビルド・E2E・実機更新や main への統合を、検証のために暗黙に実行しない。

完了は要求・条件・観測結果で判断する。テスト件数やレビュー回数を根拠にしない。最終差分に対するビルドと検証、共通判断の所有者と利用側、残る未検証事項を報告し、未実施の Apple／実機検証を含めて「完全検証済み」としない。
