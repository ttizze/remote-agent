# 会話モデルと同期の再設計計画

Host が持つ会話の状態、その保存、クライアントへの同期、provider の実行を一つの構造にまとめる。既存の操作・表示は維持する。完了した項目は文書から除き、全体の完了時に削除する。

この文書は設計と判断根拠を記録する。各決定には、理由、根拠(Bex の現状と参照実装のコード位置)、退けた案を書く。根拠のない決定は置かない。

## 判断の基準

- 一つの事実は一つの場所に、一つの表現で持つ。同じ事実の写しを同期し続ける構造を作らない。
- 識別子、保存、順序のそれぞれに所有者を一つ置く。
- 判断は必要な値だけを受け取る純粋な関数にし、副作用は資源の所有者が行う。
- 実装の規模、書き直しの範囲、移行の手間は判断の理由にしない。設計としての良し悪しだけで決める。
- 参照実装は根拠であって手本ではない。同じ問題を解いた実装が複数ある場合は読み比べ、一致している点は採り、割れている点は理由を書いて選ぶ。
- 利用者に見える機能は一つも削らない。

## 現状の構造と問題

現状のコード位置は `bce3486e4` 時点のもの。

### 同じ会話の内容が二つの経路で届く

- 読み取りはウィンドウ全体を版番号付きで返す(`crates/host-daemon/src/host_rpc/service/sessions.rs:589`)。
- ライブ更新 `SessionUpdate` は差分で、版番号も連番も持たない(`crates/agent-protocol/src/session.rs:1326`)。
- 順序を比べる手段が片方にしかないため、core に防御が散らばる。`stale()` が 4 か所(`crates/agent-core/src/state/operations/sessions.rs:426`、`:669`、`:881`、`:942`)、`already_current` と `superseded`(同 `:745`、`:829`)、適用の失敗を取りこぼしとみなす読み直し(`crates/agent-core/src/state/notifications.rs:384`)。

### 実行中と保存済みの状態を二つの経路で扱う

- 実行中のターンは `SessionActor.timeline` がメモリに持つ(`crates/host-daemon/src/host_rpc/session_actor.rs`)。
- 完了したターンだけ SQLite に書く。完了後に届いた更新は保存済みターンへ当てる別経路になる(`crates/host-daemon/src/host_rpc/routing.rs:684`、158 行の一関数)。
- 読み取りはメモリと SQLite を `overlay` で合成する。

### 識別子の所有者が揃っていない

- 会話の識別子 `SessionRef { provider, id }` は「最初の provider に属する住所」である(`crates/agent-protocol/src/session.rs:30`)。新規会話の `id` は、`bex-task:` に、クライアントが割り当てた最初の入力の識別子を続けたものである(`crates/host-daemon/src/host_rpc/service/preparation.rs:41`)。外部で作られた会話は provider の識別子がそのまま入る。
- 新規会話の識別子はクライアントの値から決まるのに、クライアントはそれを Host の応答で受け取る。それまで送信前の下書きを仮のキーで持ち、後で付け替える(`crates/agent-core/src/state.rs:106` の `DraftKey::Local`、同 `:410` の `draft_sessions`)。
- ターンと項目の識別子は provider のものを使う。provider がターン識別子を再利用するため、項目の重なりで出現を照合する(`turn_index`、`matches_occurrence`、`shares_items` が 21 か所)。
- 送った入力と provider が返すユーザー発言を `client_input_id` で突き合わせる(25 か所、`reconcile_pending` など)。

### 実行のワークフローが別々に進む

準備(`service/preparation.rs:276`)、キュー(`service/queue.rs:85`)、容量超過の再試行(`service/capacity.rs:273`)、provider 切替(`service/conversations.rs:705`、267 行)が、それぞれ別にタスクを起動し、別に保存し、別に再起動時の復旧を持つ。部品は揃っている。送信の振り分けは純粋な関数(`host_rpc/submission.rs:30`)、準備は段階を保存しながら進む、provider 切替は一歩ごとに保存する。足りないのは、それらを一つの所有者と一つの保存先に置くこと。

## 設計と判断根拠

### 決定 1: 識別子はアプリが持ち、作る側が割り当てる

会話、入力、ターン、項目、要求の識別子はアプリのものとする。会話と入力はクライアントが割り当て、入力の識別子は配送後にそのままユーザー発言の項目の識別子になる。ターンと、それ以外の項目は Host が割り当てる。provider の識別子は、Host だけが読む表に持ち、クライアントには送らない。

**既存の識別子は変えない。** 利用者が決めた(2026-11-11)。会話の識別子は、Host、通信、各端末に保存された下書きとキャッシュ、ワークツリーの記録、通知の登録、履歴を読むコマンドで使われている。付け替えると、どれがどの会話のものかを失い、後から直せない。

- 既存の会話の識別子(provider と id の組)は一字も変えない。移行は識別子を書き換えず、対応表も持たない。
- Bex で新しく作る会話の識別子は、provider を含めない。クライアントが下書きを作ったときに乱数の UUID を割り当て、それがそのまま会話の識別子になる。T3 Code と同じ形である。利用者が決めた(2026-11-11)。
- 型は今の `SessionRef` を使い、provider を省けるようにする。provider を持つ識別子と持たない識別子は、id が同じでも別の会話である。
- provider の側で作られた会話(外部で始めた会話、provider が作るサブエージェント)は、取り込む前から、provider とその provider の識別子の組で一覧に出ている。その組を識別子として使い続ける。
- 識別子から今の provider を読み取らない。今の provider は会話の行が持つ。
- 入力の識別子は、会話の識別子とは別に、入力ごとにクライアントが割り当てる。現状は会話の `id` を最初の入力の識別子から作るが、新しい会話ではそうしない。
- 既存のターンと項目の識別子は、会話の中で一意なものをそのまま使う。新しく作るものから、Host が割り当てる。provider が使い回したために同じ識別子を持つ既存のターンは、行を区別できないので、移行で一意な識別子を振る。ターンと項目の識別子は、会話の識別子と違って端末のキャッシュの中にしかなく、キャッシュはスナップショットで置き換わる。
- 下書きは、作ったときから会話の識別子で持つ。送信の前後で付け替えない。端末は「このプロジェクトで書きかけの新規会話」から、その下書きの識別子への対応を持つ。現状は仮のキーがこの役割を兼ねている(`crates/agent-core/src/state.rs` の `DraftKey::new_chat`)。
- 更新の時点で端末に残っている送信前の下書きは、Host にまだ識別子がないので、新しい識別子を割り当てる。

- **理由**: 識別子が生まれた時点で確定していれば、クライアントと core は付け替えも突き合わせもしない。下書きは最初から会話の識別子で持てる。送った入力はそのままユーザー発言になる。
- **残る対応付け**: provider との対応付けはなくならない。Host の provider との境界(接続と取り込み)に集める。
  - 配送した入力と、provider が返すユーザー発言。provider の識別子を対応として記録し、行は増やさない。
  - provider のターン、項目の識別子と、アプリのターン、項目。provider の識別子は発行した範囲の中でしか一意でないので、セッション、試行、識別子の組で対応を持つ(「保存の形」の「provider の識別子の範囲」)。
  - 取り込み。同じ組で既存の行を見つけ、二重に作らない。
- **根拠(Bex)**: 上の「識別子の所有者が揃っていない」のうち、クライアントの付け替え(`DraftKey::Local`、`draft_sessions`)と core の突き合わせ(`reconcile_pending`)がなくなる。出現の照合は Host の境界の一か所に移る。
- **根拠(参照実装)**: 読んだ全実装が同じ答えである。
  - T3 Code: 会話、実行、発言、項目がすべてアプリの識別子で、provider 側は `ProviderThread`、`ProviderTurn` として別に持つ。会話の識別子は、クライアントが下書きを作るときに乱数の UUID で決め(`apps/web/src/lib/utils.ts:51`、`apps/web/src/composerDraftStore.ts:2614`)、会話を作るコマンドに入れて送る(`packages/contracts/src/orchestrationV2.ts:2946`)。provider は識別子に含めない。プロジェクトから下書きへの対応も端末が持つ(`composerDraftStore.ts` の `logicalProjectDraftThreadKeyByLogicalProjectKey`)。
  - Happy: 「provider の識別子を使ってはならない」と明記する(`docs/session-protocol.md` の Subagents)。
  - Paseo: 本文の一致で突き合わせていたのを「クライアントの識別子で行が生まれ、以後変わらない」に改めた(`docs/timeline-sync.md` の canonical submitted row)。
  - OpenCode: 同じ識別子での再送は最初の受付が勝つ(`specs/v2/session.md` の Prompt Admission)。
- **退けた案**:
  - 識別子を Host の応答で受け取る現状。クライアントが送信前に識別子を知らないので、付け替えが残る。
  - 新しい会話にも provider を含める。形は一種類で済むが、provider は送信するまで決まらないので、下書きの段階で識別子が確定せず、端末の中の付け替えが残る。
  - 会話の識別子を provider を含まない新しい形に振り直す。形は整うが、既存の参照をすべて付け替えることになり、戻せない。

### 決定 2: 会話の正本は Host の一つの DB

会話に関する永続状態はすべて一つの SQLite に置く。provider の履歴は、外部で続けられた会話を取り込むときの入力としてだけ読む。

- **理由**: 一つのトランザクションで一貫した変更ができる。複数ファイルを跨ぐ復旧が要らない。
- **根拠(参照実装)**: T3 Code は `statev2.sqlite` 一つ。OpenCode v1.2 は多数の小さなファイルから一つの SQLite に移した。Paseo だけが provider の履歴を正本にしてメモリに投影を持ち、その結果「捨てた途中経過は復元できないので分岐を拒否する」という制約を負っている(`docs/timeline-sync.md` の Durable item anchors)。
- **退けた案**: provider を正本にする。provider 切替後の会話は一つの provider の履歴では表せない。

### 決定 3: 対象は五つ、一つの事実に一つの表現

| 対象 | 内容 |
|---|---|
| `Thread` | 会話。作業フォルダ、モデル選択、既読、名前、親子関係、キューの保留 |
| `Input` | 受け付けたが、まだ会話に入っていない入力 |
| `Turn` | 実際に始まった実行 |
| `Item` | 発言、推論、コマンド、変更、ツール、計画など |
| `Request` | 承認と質問 |

provider との対応、実行の試行、引き継ぎは Host だけが持ち、クライアントには送らない。

- **理由**: 表現が一つなら、写しを同期する処理が存在しない。クライアントは表示に使うものだけを受け取る。
- **根拠(参照実装、反例)**: T3 Code はアシスタントの本文を `ConversationMessage`(`packages/contracts/src/orchestrationV2.ts:1313`)、`TurnItem` の `assistant_message`(同 `:1640`)、`ExecutionNode`(同 `:770`)に持つ。上流は重複を通信上で省くための印 `textOmitted: DedupedBodyMarker` を足している(同 `:866`、`:1640`)。クライアントへ送る `ThreadProjection` は provider の内部情報を含む 17 種の配列である(同 `:2038`)。
- **根拠(参照実装、正例)**: OpenCode の表は会話、メッセージ、部品、受信箱の四つ(`packages/core/src/session/sql.ts`)。Bex の現状も `Turn` と `Item` の一系統で、ここは維持する。
- **退けた案**: T3 Code の対象をそのまま採る。挙動を T3 Code に合わせることと、対象の重複まで写すことは別である。照合は対応表で行う。

### 決定 4: `Input` と `Turn` を分ける

`Input` は準備中、キュー、配送中、結果不明、失敗のいずれかで、配送されるとユーザー発言の `Item` になり `Input` の行は消える。`Turn` は実行が始まってから作る。

- **理由**: 「頼まれたこと」と「実行したこと」は寿命も状態も違う。分ければ、実行前のためだけの空の項目がなくなる。送信中、キュー、steer、準備、取り消しが同じ仕組みになる。
- **根拠(参照実装、反例)**: T3 Code の `Run` は状態に `preparing` と `queued` を含み、そのために `providerThreadId`、`rootNodeId`、`activeAttemptId`、`startedAt`、`queuePosition` が状態と無関係に空になれる(`orchestrationV2.ts:683`)。
- **根拠(参照実装、正例)**: OpenCode は入力を受信箱に保存し、配送の種類(`steer`、`queue`)を持たせ、配送時に会話へ移す(`packages/schema/src/session-inbox.ts:11`、`specs/v2/session.md`)。
- **根拠(Bex)**: 現状は `PendingSubmission`(クライアント)、`SubmissionDelivery`、`InputQueue`、`Startup` と `SessionPreparation` の四つが同じ「まだ会話に入っていない入力」を別々に表す。
- **退けた案**: キューを「状態が queued の実行」で表す T3 Code の形。

### 決定 5: 状態は行、行に連番。イベント表は持たない

書き込みトランザクション一回に Host 全体で一本の連番を一つ割り当て、変更した行すべてにその連番を付ける。「連番 N より後の変更」は連番が N より大きい行である。削除は連番付きの削除記録で表し、一定期間で消す。

- **理由**: 変更の内容を「対象全体の上書き」にする(決定 6)なら、イベントを並べた表は行の内容の写しになる。同じ事実を二か所に持たない。投影の更新処理も圧縮も要らない。
- **成立する条件**: 行の最新だけでは、過去のトランザクション一回分は復元できない。再接続では「ある時点までに変わった行の最新と削除」をまとめて渡す。これで一致する条件は「同期の契約」に書く。条件を満たせない場合(削除記録が消えた後のカーソルなど)はスナップショットに落とす。
- **根拠(参照実装)**:
  - Replicache の Global Version 方式は、全体の版をカーソルにし、それ以降に変わった対象の上書きと削除を返す。イベント表を持たない同期の実例である。
  - OpenCode はイベント本体の保持が任意で、コード上の既定は保持なし(`packages/core/src/bus.ts:190`)。連番の更新と表の更新を一トランザクションで行う(同 `:310-435`)。
  - T3 Code の上流は、イベントを投影が反映した後に一日で消す(`apps/server/src/orchestration-v2/ProjectionMaintenance.ts:42`)。イベントからの作り直しは試験用に移り、「本番は投影が反映済みのイベントを消すので、再生しない」と書かれている(`testkit/ProjectionReplay.ts:29`)。これが示すのは「正本はイベントではなく行」までである。T3 Code は再開用の末尾としてイベント表を持ち続けており、イベント表が不要である証明にはならない。
- **退けた案**:
  - イベントを正本にして表を導出する。作り直しと監査ができるが、Bex にその利用者がいない。
  - 再開用に短命なイベントの末尾を持つ(T3 Code の現在の形)。再接続でトランザクション単位の再生ができるが、行と同じ内容を一定期間二重に持つ。行の最新をまとめて渡す形で一致するなら要らない。
- **保持**: 削除記録は一日で消す。T3 Code がイベントを残す期間と同じにする。利用者が決めた(2026-11-11)。受付記録は消さない(決定 8)。

### 決定 6: 同期は行の版による上書き。ライブは変更セット単位

上書きは対象全体と、その行の版(最後に変えたトランザクションの連番)を運ぶ。クライアントは行ごとに版を持ち、届いた版のほうが新しいときだけ置き換える。

同期の基本は次の三つである。

- **ライブ**: トランザクション一回分を一つの変更セットにする。
- **追いつき**: 再接続したクライアントに、カーソルより後に変わった行の最新と削除を、ある時点でまとめた一つの変更セットにする。途中のトランザクションの境界は含まない。
- **スナップショット**: カーソルがない、または追いつきの条件を満たさないときに、範囲の全行を送る。

カーソルは、クライアントが完全に持っている範囲(会話ごと、一覧)ごとに一つ持つ。値は保存領域の識別子と連番の組である。遅い接続は上限を超えたらその接続だけを切り、クライアントはカーソルから再開する。会話の範囲に関するものは、過去の項目も省いた本文も含めて、すべて購読の一本の流れで、所有者が決めた順に届く。操作の応答は受付の結果だけを返し、状態を運ばない。開いたときのウィンドウは現状の 10 ターンを維持する(`service/transcripts.rs:12`)。

規則の全体と具体例は「同期の契約」に書く。

- **理由**:
  - 状態が届く経路を購読の流れ一本にすれば、届いた順に適用するだけで Host と一致する。現状の経路ごとの防御は、経路が複数あるために要る。
  - 行の版は、追いつきで「カーソルより後に変わった行」を選ぶために要る。クライアントが新しい版だけを適用する規則は、再接続の境目で同じ行が二度届いても害がないことを保証する。
  - 上書きは同じものを二度当てても結果が変わらず、同じ対象の古い版は飛ばせる。差分は一つ抜けると壊れる。飛ばせるのは同じ対象の古い版だけで、別の対象の変更は飛ばせない。追いつきが「カーソルより後に変わった全対象」を含むのはそのためである。
  - 変更セット単位なら、「入力が消えて発言がまだない」のような途中の状態を表示しない。
- **連番を Host 全体で一本にする理由**: これは「現状のライブ更新に順序がない」問題とは別の選択である。その問題は会話ごとの連番でも解ける。全体で一本にするのは次の理由による。
  - `Thread` の行は、会話の範囲と一覧の範囲の両方に属する。ターンの完了は `Turn` と `Thread` を同じトランザクションで変える。連番が一本なら、行の版は一つで済む。
  - 一覧は会話を跨ぐので、Host 全体の順序が要る。会話にも同じ連番を使えば、順序が二種類にならない。
- **根拠(Bex)**: 現状は RPC の応答ごとに別のストリームを使う(`crates/agent-protocol/src/protocol.rs:1`)。過去ページや項目の本文の応答と、ライブ更新との間に順序の保証がない。状態を応答で返す限り、古い応答が新しい状態の後に届く場合を個別に防ぐことになる。
- **根拠(参照実装)**:
  - T3 Code はイベントが対象全体の上書きで(`orchestrationV2.ts:1992` の `message.updated`)、クライアントの適用は 421 行で済んでいる(`packages/client-runtime/src/state/orchestrationV2Projection.ts`)。再開は、差が小さければ再生、そうでなければスナップショットで、購読してから読む(`apps/server/src/orchestration-v2/ThreadStream.ts:100`、`apps/server/src/ws.ts:884`)。
  - 遅い接続を切る方式は T3 Code(`LiveStreamBudget.ts`)と OpenCode(`specs/v2/event-stream-architecture.md` の Delivery Law)で一致する。Bex も上限を持つ(`routing/connections.rs:4`)。
  - カーソルに世代を持たせるのは Paseo(`docs/timeline-sync.md` の `{ epoch, seq }`)。Bex には接続開始時に比べる保存領域の識別子がすでにある(`providers/registry.rs:187`)。
- **根拠(反例)**: Paseo は「ライブの差分」と「正しい履歴の取得」の二経路で、設計文書の大半がその突き合わせの規則である(元の連番の範囲、二本のレーン、世代の変更時の扱い)。Bex の現状と同じ構造の行き先を示している。
- **退けた案**:
  - 行ごとに流す。複数の対象に跨る変更が途中で見える。
  - 連番を会話ごとにする(OpenCode)。一覧のために別の順序が要り、両方の範囲に属する `Thread` の行が版を二つ持つ。
  - カーソルを一つにする。会話 A を読んで進んだカーソルは、未取得の会話 B について何も保証しない。
- **確認が要る点**: 行の版を比べる規則は Replicache の Row Version 方式と Happy の版付きの欄(`docs/protocol.md:17`)に近いが、同じ規則の実装を読んだわけではない。

### 決定 7: 本文は区切りごとに項目全体を送る。コマンド出力は同期の外で流す

T3 Code と同じ形にする。利用者が決めた(2026-11-11)。一文字ずつの差分は同期に載せない。

- **アシスタントの本文と推論**: 所有者は provider から届く差分をためる。Markdown の区切りで、最短 400 ミリ秒の間隔を空けて、項目全体を保存して上書きとして送る。区切りが来ないまま 800 ミリ秒止まったら、たまった分を送る。項目の完了でも送る。
- **コマンド出力**: 実行中の出力は同期に載せない。クライアントは、その行を展開している間だけ、項目ごとの出力の流れを購読する。Host は、追記を最短 100 ミリ秒の間隔で送り、購読者が遅れたら末尾の全体を送り直す。途中から購読したクライアントには、最初に末尾を送る。項目が完了すると、保存した出力は項目の行に入る。保存するのは出力の末尾 64 KiB で、それより前を捨てたことを印で示す。

- **理由**: 同期が運ぶのは保存済みの行の上書きだけになる。差分の順序、取りこぼし、途中からの接続のための規則が要らない。コマンド出力は、見ている行でだけ要り、失っても完了時の出力で置き換わるので、会話の状態と分けられる。
- **根拠(参照実装)**: どちらも T3 Code の形である。
  - 本文は「Markdown の区切りで、最短 400 ミリ秒ごと」に届け、止まったら 800 ミリ秒で送る(`apps/server/src/orchestration-v2/assistantStreaming.ts:113`、`:73`、`:160`)。項目全体を運ぶ(`packages/contracts/src/orchestrationV2.ts:1992`)。
  - 保存する出力は末尾 64 KiB である(`packages/shared/src/terminalOutput.ts:39`、`apps/server/src/orchestration-v2/CommandOutputHub.ts:93-99`)。
  - コマンド出力は「同期のイベントを通さない。展開した行が、末尾、まとめた追記、保存した出力の順に受け取る」(`apps/server/src/orchestration-v2/CommandOutputHub.ts:29`)。送る間隔は 100 ミリ秒、遅れた購読者には末尾を送り直す(同 `:32-36`)。項目の行は、出力を省いたことを示せる(`orchestrationV2.ts:1699` の `outputOmitted`)。
- **変わる表示**: 本文は現状の一文字ずつから、区切りごとになる。コマンド出力は、展開した行で流れる。長いコマンド出力は、完了後は末尾 64 KiB だけが残る。
- **退けた案**: 一文字ずつの差分を同期に載せる。表示は細かいが、差分に基準の版と開始位置を付け、保存の通知と回復の手順を持つことになる。T3 Code に手本がなく、自前で保ち続ける部分になる。レビューで見つかった同期の穴の半分がここから出た。

### 決定 8: 書き込みは受付と、会話ごとの所有者のループ

クライアントの操作は、クライアントが割り当てた操作の識別子を付けて送る。Host は操作の効果と同じトランザクションで受付記録(操作の識別子、対象の会話、結果)を書く。拒否も記録する。同じ識別子の操作が再び届いたら、記録した結果を返して何もしない。受付記録は消さない。送信では入力の識別子が操作の識別子を兼ね、`Input` の行を保存した時点で受付完了とする。

会話ごとに所有者のタスクを一つ置く。所有者は、会話に届く入力を一つずつ純粋な関数に渡し、その結果を書き込んでから実行する。

```text
入力: 操作 | provider のイベント(試行で識別) | 動作の結果 | 時刻 | 再起動
step(状態, 入力, 時刻, 識別子の元) -> { 行の変更, 動作, 仕事, 応答, 受付記録 }
```

- `step` は純粋な関数である。時刻と、Host が割り当てる識別子の元は入力から受け取るので、同じ入力から同じ結果になる。
- 行の変更、仕事、受付記録は、一つのトランザクションで書く。応答はその後に返す。
- **動作**は provider への呼び出しである。作業フォルダの準備、対応の確保、配送(開始か steer)、中断、回答、巻き戻し、分岐がこれに当たる。呼ぶ前に、それを示す途中の状態を行に書いておく。結果は「動作の結果」として次の入力になる。再実行してよいとは限らないので、途中で落ちたときは決定 9 の規則で確定させる。
- **仕事**は、何度実行しても同じ結果になる副作用である。仕事表に、それを必要とした変更と同じトランザクションで書く。実行役が少なくとも一回実行し、失敗したら間隔を空けて実行し直す。結果を返す仕事は、その結果を「動作の結果」として所有者へ渡す。

所有者は、やることが残っているか、購読者がいる間だけ存在する。会話の行の書き込みと、購読への送信は、所有者だけが行う。

所有者は実行の試行ごとに世代を持つ。provider から届いたイベントは現在の試行のものだけを受け取り、前の試行から遅れて届いたものは捨てる。

仕事は、外部の会話の取り込み、タイトル生成、添付の削除、ターミナルの後片付け、provider のセッションの切り離し、ほかの会話への受け渡しである。ほかの会話への受け渡しは、会話の行を書くのはその会話の所有者だけ、という規則のために要る。provider が作るサブエージェントのイベントは親の provider から届くので、親の所有者が子の所有者へ渡す。受け渡しを仕事にすれば、親が書いた後に落ちても子に届く。

- **理由**:
  - 判断を純粋な関数にすれば、記録した入力を流すだけで試験できる。provider の記録を流す試験(検証)はこの形を前提にする。
  - provider への呼び出しは、落ちた後に再実行してよいとは限らない。T3 Code も「落ちたら無効なもの」として分けている。途中の状態を行に持てば、再起動時の扱いを状態ごとに決められる。何度実行してもよい副作用だけを仕事表に置く。
  - 対象の識別子だけでは、別々の操作を区別できない。改名を二回した後に一回目の再送が届くと、名前が戻る。配送後に `Input` の行を消し、巻き戻しでその発言も消した後は、同じ送信の再送を止める手がかりが行に残らない。操作の識別子と消さない受付記録で止める。
  - 所有者を一つにしても、前の試行から遅れて届く応答を弾く判定は要る。その判定を所有者の一か所に置く。
- **根拠(Bex)**: 判断はすでに純粋な関数である(`host_rpc/submission.rs:30`)。準備は段階を保存しながら進む(`service/preparation.rs:276`)。現状は準備、キュー、再試行が別々にタスクを起動する。会話の状態は `Arc<Mutex<SessionActor>>` と、接続とは分離した活動のロックの下にある(`host_rpc/routing.rs:109`)。
- **根拠(参照実装)**:
  - OpenCode は入力の受付と実行を分ける。実行は会話ごとに一つで、起こす合図は重ねても一回にまとまる(`specs/v2/session.md` の Execution Is Process-Local)。実行は毎回、保存された履歴を読み直して次を決める。
  - T3 Code はコマンドの識別子ごとに受付記録を、効果と同じトランザクションで書く(`apps/server/src/orchestration-v2/EventSink.ts:166`)。拒否も記録する(同 `:188`)。同じ識別子が別の会話に使われたら衝突として拒否する(`Orchestrator.ts:333`)。イベントは一日で消すが、受付記録は冪等のために残す(`ProjectionMaintenance.ts:256`)。
  - 古い実行の遮断は T3 Code の `writeIfRunCurrent`(`EventSink.ts:123`)。
  - T3 Code は副作用を「落ちても再実行してよいもの」(セッションの切り離し、巻き戻し、後片付け、タイトル生成など)と「落ちたら無効なもの」(ターンの開始、steer、中断、回答)に分ける(`EffectOutbox.ts:125`、`:138`)。前者が仕事表、後者が途中の状態に当たる。
  - PR #55 は、会話ごとの actor が `ThreadMachine::step(状態, 入力)` で書き込みと副作用と応答を返す形で実装した(`crates/agent-domain/src/machine.rs:6804`、`model.rs:1652`)。時刻と識別子の元を入力から受け取る。副作用は 10 種で、待ち行列に書いて実行役が実行する(`model.rs:1477`、`crates/agent-runtime/src/outbox/mod.rs`)。ほかの会話へのコマンドも副作用の一つである(`SendToThread`)。
- **退けた案**:
  - provider への呼び出しも待ち行列に入れる(T3 Code、PR #55)。待ち行列の行と、途中の状態を表す行が、同じことを二か所で表す。再起動時の規則も、待ち行列の行と会話の状態の両方を見ることになる。
  - 保存された状態だけから次の動作を決め、入力を受け取らない(この計画の前の版)。provider のイベントや動作の結果を状態に書いてから読み直すことになり、記録した入力を流す試験ができない。ほかの会話への受け渡しも書けなかった。
  - 対象の識別子だけで冪等にする。上の理由のとおり、別々の操作を区別できない。
  - 行の版の一致を操作の条件にする(Happy の `expectedVersion`、`docs/protocol.md:128`)。古い再送は拒否できるが、成功済みの操作の再送も不一致になり、一回目の結果を返せない。
- **確認が要る点**: 経路表は Host のワークフローから作り、PR #55 の副作用 10 種と照らした(「経路の対応」)。Claude と DeepSeek の接続の内部は追っていない。

### 決定 9: 途中の状態ごとに、再起動時の規則を一つ持つ

provider に副作用を起こす前に「途中」の状態を保存し、結果を得たら保存する。起動時は、各会話の所有者に「再起動」の入力を渡し、`step` が途中の状態それぞれを決まった規則で確定させる。状態は Rust の enum で持ち、規則は全ての途中の状態を網羅する。

| 途中の状態 | 再起動時 |
|---|---|
| 入力が準備中 | 保存された段階から続ける |
| 入力が配送中 | 結果不明にして利用者に確認する |
| 実行中のターン | 中断にしてキューを保留する。更新による再起動なら継続の入力を一つ入れる |
| 対応への履歴の注入中 | その対応を捨てて作り直す |
| 要求への回答の送信中 | 結果不明にする。ターンが中断なら要求を閉じる |
| 待機中のターン(再試行の時刻あり) | 時刻から待ち直す |

- **理由**: 規則が状態の定義と同じ場所にあれば、書き漏れをコンパイラが検出する。復旧のための別の仕組みが要らない。
- **根拠(Bex)**: 各規則は現状の挙動と同じである。配送の結果不明(`service/queue.rs:157`)、キューの保留(同 `:100`)、注入が曖昧なら新しい対応にする(`service/conversations.rs:846` 付近のコメント)、更新後の継続(`service/update.rs:87`)。現状はそれぞれ別のファイルにある。
- **根拠(参照実装)**: OpenCode は実行の開始時に先行書き込みの印を残し、成功、失敗、中断で外す。起動時に印が残っていれば続きを行い、実行中のまま残ったツール呼び出しを失敗にする(`specs/v2/session.md` の Recovery Boundaries)。T3 Code は再起動時にキューを保留する。PR #55 は再起動を状態機械の入力にし、キューの保留、待っている要求の失効、実行中の試行の終了、更新後の継続を一つの関数で決める(`crates/agent-domain/src/machine.rs:6470`)。
- **退けた案**: 状態を文字列と空になれる項目で表す(T3 Code の `Run`)。ありえない組み合わせを作れてしまう。

### 決定 10: provider の対応を履歴に合わせる処理は一つ

Host は会話ごと、provider ごとに対応(provider のセッションと、そのセッションが知っている履歴の範囲)を持つ。配送の前に「この対応が会話の履歴を N 件目まで知っている状態にする」処理を一つだけ通す。provider が自前の巻き戻しや分岐を持てばそれを使い、なければ新しいセッションを作って履歴を渡す。

provider 切替、巻き戻し、分岐は、会話の行を一トランザクションで変えるだけにし、provider 側の調整は次の配送時にこの処理が行う。

- **理由**: 三つの操作は「対応が履歴と合っていない」という同じ状況を作る。合わせ直す処理が一つなら、操作ごとの手順が要らない。
- **根拠(Bex)**: 部品はすでにある。対応が知っている件数 `Binding.covered`、取り込みの範囲 `Segment`、渡した履歴 `Handoff`(`host_rpc/conversations.rs:20-52`)。現状は provider 切替(`service/conversations.rs:705`)、巻き戻し(同 `:95`)、分岐(同 `:220`)が別々の手順になっている。
- **根拠(参照実装)**: T3 Code は `ContextHandoff`、`ContextTransfer` と、接続口の巻き戻し、分岐で同じことをする。
- **退けた案**: 分岐で履歴を親から参照する(T3 Code の `visibleTurnItems` の `inherited`)。読み取りのたびに親子を辿る。行を写す(OpenCode の分岐は選んだ境界までを写す)。

### 決定 11: provider の接続口は会話の実行に絞る

接続口は、セッションを開く、閉じる、スレッドの確保、ターンの開始、steer、中断、要求への回答、巻き戻し、分岐、能力の問い合わせ、イベント列とする。アカウント、モデル一覧、権限、設定は別の接続口に分ける。

- **理由**: 実行の所有者が必要とするのは実行の操作だけである。provider 固有の操作を共通の口に置くと、他の provider が「未対応」を返す既定実装を持つことになる。
- **根拠(Bex)**: `Agent` は約 35 操作で、`codex_cli`、`dsh_credentials`、`account_terminal` が既定実装付きで入っている(`crates/host-daemon/src/providers/mod.rs:275-310`)。一覧と履歴の読み取りは、正本が Host の DB になれば取り込みでしか使わない。
- **根拠(参照実装)**: T3 Code の接続口は実行に絞られている。

### 決定 12: クライアントの状態は変更セットの適用結果だけ

core は会話の複製を持ち、変更セットを適用する。適用関数は protocol クレートに置き、Host と共有する。下書きは会話の識別子で持つ。`Intent` のうち会話への操作はコマンドになる。端末のキャッシュはカーソルと状態を保存し、開くときはキャッシュを表示してカーソルから購読する。

表示の投影(`presentation`)の出力は変えない。入力が複製に替わるだけである。

- **理由**: 状態の書き手が一つになる。経路ごとの版番号の防御は、行の版を比べる一つの規則に置き換わる。仮キーの付け替えと送信の突き合わせはなくなる。
- **根拠(Bex)**: 置き換わるものは「現状の構造と問題」のとおり。適用関数を共有する形は現状と同じ(`crates/agent-protocol/src/session.rs:365`)。
- **根拠(参照実装)**: T3 Code の端末キャッシュは連番と状態を保存し、連番から再開する(`packages/client-runtime/src/state/threads.ts`)。

### 決定 13: 一覧も同じ連番で同期する

サイドバーの一覧を、会話と同じ規則で同期する。利用者が決めた(2026-11-11)。

- **範囲**: すべての会話の要約と、登録済みのプロジェクト。床は持たない。
- **要約**: `threads` の行のうち、一覧に出す値である。名前、状態、最後の発言の抜粋、未読、親、今の provider、更新時刻。
- **同期**: 会話と同じく、スナップショット、追いつき、ライブの三つで届く。カーソルは一覧に一つ持つ。
- **件数の制限**: プロジェクトごとに数件だけ出し、「もっと見る」で増やす表示は、端末が持っている範囲から作る。Host へは問い合わせない。
- **provider の側の会話**: 仕事が provider の一覧を読み、`threads` の行にする。一覧は行だけから作る。履歴の取り込みは、会話を開いたときに行う。
- **同期に載せないもの**: 検索は問い合わせと応答のままにする。変更の有無、ブランチ、プロジェクトのアイコンは、git とファイルから読む値なので、読み取りのままにする。
- **Host の中の利用者**: 通知と Live Activity は、一覧の変更を購読して送る。実行中、待ち、未読の一覧を別に配る通知はなくなる。

- **理由**: 会話の状態が変わるとき、一覧の要約も同じトランザクションで変わる。同じ連番で、それぞれがどの時点の状態かを比べられる。別々の購読の到着・適用時刻が一致する保証はない。一覧のための版番号、ページ、通知の突き合わせが要らなくなる。
- **根拠(Bex)**: 現状の一覧は、provider の一覧、登録済みのプロジェクト、Host の会話を読むたびに合成する(`crates/host-daemon/src/host_rpc/service/titles.rs:1`)。変更は版番号(`host_rpc/routing.rs:104` の `list_revision`)と、更新、改名、活動の通知で伝え、core がページごとに突き合わせる(`crates/agent-core/src/state/operations/lists.rs`)。利用者の Host の会話は 363 件で、全件の要約を一度に送っても小さい。
- **根拠(参照実装)**: T3 Code は一覧を一本の流れで送る。スナップショットは会話の要約とプロジェクトを含み、その後は会話とプロジェクトの更新と削除が連番付きで届く(`packages/contracts/src/orchestrationV2.ts:2250-2290`)。要約は一覧のための値だけを持つ(同 `:2099`)。差が 1,000 件を超えたらスナップショットを送り直す(`apps/server/src/ws.ts:687`)。検索は別の問い合わせである(`apps/server/src/orchestration-v2/ThreadSearch.ts`)。
- **退けた案**: 一覧を更新時刻の床で区切る。件数が多い Host では最初に送る量が減るが、「もっと見る」が Host への問い合わせに戻り、プロジェクトごとの件数の制限と床の関係を定めることになる。今の件数では要らない。件数が増えて最初の同期が重くなったら、T3 Code と同じく古い会話を別に分ける。
- **確認が要る点**: provider の一覧を読む仕事の間隔と、provider の側で消えた会話の扱い。別のブランチで進んでいる「完了した会話の整理」は `threads` の行の値として載せる。

## 同期の契約

決定 5、6、7、8 が成立する条件を、規則と具体例で定める。試験はこの節から作る。

### 用語

- **連番**: Host 全体で一本。書き込みトランザクション一回に一つ。
- **行の版**: その行を最後に変えたトランザクションの連番。上書きは必ず行の版を運ぶ。
- **削除記録**: 範囲から外れた行の種類、識別子、そのトランザクションの連番。行を消したときと、ターンを巻き戻し済みにしたときに書く。
- **保存領域の識別子**: DB を作ったときに決まる値。バックアップから復元して過去の状態に戻すときも再発行する。通常の形式更新では保持する。同じ識別子で連番を巻き戻すと、古い端末のカーソルが別の履歴を指すためである。
- 識別子は再利用しない。消した行と同じ識別子の行は二度と作らない。

### 範囲とカーソル

クライアントが完全に持っている行の集まりを範囲と呼ぶ。カーソルは範囲ごとに持つ。

- **項目の位置**: `Item` は会話の中での順を表す位置を持つ。位置が変わるのは、履歴の置き換えのときだけである。
- **履歴の置き換え**: 外部で続けた会話の再取り込みは、取り込んだターンを Host が記録したターンの間に入れるので、項目の位置を振り直す。Host は置き換えの連番を会話に記録する。
- **会話の範囲**: その会話の `Thread` の行、すべての `Input`、すべての `Request`、床のターンに属する床以上の位置の `Item` と、それより後のターンの `Item` の行すべて、床のターンの順序番号以降の `Turn` の行すべて。床は、項目の位置とターンの順序番号の組である。削除後もその境界を保持し、項目がまだない実行中のターンもターンの境界以降なら含める。空の会話の床は両方を 0 とする。範囲の順はターンの順序番号、同じターンなら項目の位置で比べる。古いターンに遅れて追加された項目の位置が、新しいターンの項目より大きくても、後のターンの項目を範囲から落とさない。
- **カーソル C の意味**: 範囲内の全行について、連番 C 時点の最新を持っている。
- カーソルは範囲を跨いで使えない。会話 A のカーソルは、会話 B について何も保証しない。
- 範囲内の項目の行はすべて持ち、大きな本文だけを省く。現状はターンごとに要約の項目だけを持てるが(`items_summary`、`crates/agent-protocol/src/session.rs:1255` の突き合わせ)、ターンの中身が部分的だと「完全に持っている」を定義できない。
- 床を項目の位置にするのは、一つのターンが非常に大きいときに、ターンの途中でウィンドウを区切れるようにするためである。T3 Code は、ウィンドウを 10 ユーザーターン、1 ターン 500 項目、1 MiB で区切り、長いターンの内側でも止める(`apps/server/src/orchestration-v2/threadHistoryPaging.ts:11-21`)。本文を省いた項目は一件ずつ読む(`packages/contracts/src/orchestrationV2.ts:4177`)。
- **一覧の範囲**: すべての会話の `Thread` の行のうち一覧に出す要約と、すべての `Project` の行(決定 13)。床は持たない。カーソルは会話の範囲とは別に一つ持つ。`Thread` の行は会話の範囲と一覧の範囲の両方に属する。

### Host が送るもの

会話の範囲に関するものは、すべて購読の一本の流れで届く。Host は購読ごとに、そのクライアントの床を持つ。

- **スナップショット**: 一貫した読み取り時点 H での範囲の全行。H と床を含む。
- **追いつき**: クライアントのカーソル C と床を受け取る。範囲内で版が C より大きい行の最新と、連番が C より大きい削除記録を、一貫した読み取り時点 H でまとめる。
- **ライブ**: トランザクション一回分のうち、購読の床以上の範囲に触れた上書きと削除。ただし履歴を置き換えたトランザクションはライブの変更セットにせず、その位置にスナップショットを一つ送る。
- **範囲の拡張**: 新しい範囲に入り、それまでの範囲になかった行。Host は送ると同時に購読の床を下げる。
- **項目の再送**: クライアントが求めた項目の、本文つきの現在の行。

実行中のコマンド出力は、この流れに載せない。項目ごとの別の流れで送る(決定 7)。失っても会話の状態は変わらない。

会話の行を書くのは、その会話の所有者だけである。改名や既読のような操作も、仕事表の結果も、所有者を通して書く。例外は新しい会話の行を最初に作るときで、分岐やサブエージェントでは親の所有者が子の最初の行を同じトランザクションで作る。

購読の登録、読み取り、送信も所有者が直列に処理する。したがって、流れの中のどの位置でも、それまでに送ったものを順に適用した状態は、その時点の Host の範囲と一致する。範囲の拡張も項目の再送も、その時点までのライブをすべて送った後、次のライブより前に送る。

追いつきを返せるのは、次のすべてを満たすときだけである。満たさなければスナップショットを返す。

- 保存領域の識別子が一致する。
- C が現在の連番以下である。
- C より後の削除記録がすべて残っている。削除記録を消し終えた連番を P とすると、C ≥ P である。
- C が、その会話の最後の履歴の置き換えの連番以上である。置き換えの連番で取ったスナップショットのカーソルは、置き換えの後の状態を持っているので有効である。

履歴を置き換えたとき、所有者は購読中のクライアントに、そのトランザクションの変更セットの代わりにスナップショットを送る。変更セットを先に送って同じ連番へカーソルを進めてはならない。位置が変わると、クライアントの床が指す内容が変わるためである。

会話が存在しなければ、その旨を返す。クライアントは範囲を捨てる。

### クライアントの適用規則

購読を張り直すたびに端末側で新しい世代を割り当て、前の購読から届いたものは捨てる。追いつきとライブは、対象範囲を完全に持つ直前のカーソルも運ぶ。直前のカーソルが手元と一致しなければ適用せず、購読し直す。連番の数値の飛びは、別の会話の変更によって起きるので許す。

- **上書き**: 持っていない行、または届いた版が持っている版より大きい行だけを置き換える。版が同じで、持っていない本文が付いていれば、本文だけを取り込む。
- **削除**: 持っている行の版が削除の連番より小さければ消す。`Turn` の削除はその `Item` を一緒に消す。巻き戻しも、クライアントには削除として届く。
- **スナップショット**: 範囲を置き換える。スナップショットに含まれない行をすべて消し、床とカーソルをスナップショットのものにする。削除記録が消えた後は、どの行が消されたかを知る手段がスナップショットしかないためである。それまでに広げていた過去の範囲も捨て、必要になったら広げ直す。
- **追いつき**: 一度に適用し、カーソルを H にする。
- 範囲外の行への上書きは捨てる。
- **ライブ**: 一セットを一度に適用し、カーソルをその連番にする。連番がカーソル以下のライブは捨てる。
- 持っている項目が巻き戻しですべて消えたら、範囲を捨てて購読し直す。

### 部分読み込み

部分読み込みは、どちらも購読の流れの中で届く。応答として別に返すと、ライブとの間に順序の保証がなく、取得中の変更が抜ける。

- **範囲の拡張**: クライアントは新しい床を求める。所有者は、新しい範囲に入り旧範囲にはなかった行を読んで流れに載せ、購読の床を下げる。古いターンに遅れて追加された項目も、そのターンが新たに範囲に入れば含める。一度に送る量には上限があるので、拡張は実際に下がった床を運ぶ。クライアントは行を取り込み、床をその値にする。それより後のライブは広がった範囲への変更を含むので、取得の前後で変更が抜けない。
- **項目の再送**: 上書きは、大きな本文を省いたことを示せる。クライアントは、本文が要るときに項目の再送を求める。所有者は、本文つきの現在の行を流れに載せる。クライアントは、版が同じでも、持っていない本文を取り込む。

### 操作と受付記録

- すべての操作は、操作の識別子と保存領域の識別子を持つ。保存領域の識別子が一致しない操作は拒否する。
- 受付記録は操作の識別子、対象の会話、結果(受付か、理由付きの拒否)を持ち、効果と同じトランザクションで書く。
- 同じ識別子の操作が再び届いたら、記録した結果を返し、何もしない。対象の会話が違えば衝突として拒否する。
- 受付記録は、巻き戻しや会話の削除の後も消さない。
- クライアントと Host の間の結果不明は、再送で結果を得て解消する。provider に届いたか不明な場合は `Input` の状態として残る(決定 9)。

### 実行中の本文とコマンド出力

- 実行中のアシスタントの本文と推論は、区切りごとに項目全体の上書きとして届く(決定 7)。ほかの上書きと同じ規則で適用する。途中から接続したクライアントは、スナップショットか追いつきで、最後に保存された本文を受け取る。
- 実行中のコマンド出力は、項目の行に入れない。行は出力を省いたことを示す。クライアントは、その行を展開している間だけ、項目ごとの出力の流れを購読する。
- 出力の流れは、追記か、末尾の全体のどちらかを運ぶ。購読の最初と、購読者が遅れたときは末尾の全体を送る。クライアントは、末尾の全体を受け取ったら手元の出力を置き換える。
- 項目が完了すると、出力の流れは終わり、保存した出力が項目の行に入る。クライアントは項目の行の出力を表示する。
- 出力の流れは保存しない。Host が落ちると実行中の出力は失われるが、そのコマンドも止まっている。

### 具体例

| 状況 | 適用される規則 | 結果 |

| カーソル 9 で切断。その間に連番 10 が項目 A、11 が項目 B を変えた | 追いつき | A と B の両方が届く。片方だけを受け取る経路はない |
| 項目 A が連番 10、12、15 で変わった。カーソル 9 で再接続 | 追いつきは行の最新 | 版 15 の A だけが届く |
| 持っている項目 X が Host で消され、その削除記録も保持期間を過ぎて消えた後に再接続 | スナップショットは範囲を置き換える | X はスナップショットに含まれないので消える |
| 床が(ターン 2、位置 100)。(ターン 1、位置 50)まで広げた後、ターン 1 の位置 75 の項目が更新される | 範囲の拡張で購読の床も下がる | 更新がライブで届く |
| (ターン 2、位置 100)から(ターン 1、位置 50)まで広げる要求と、ターン 1 の位置 75 の項目の削除が同時に起きる | 拡張はそれまでのライブの後、次のライブの前に流れに載る | 削除が先なら拡張に 75 は含まれない。後なら拡張の後に削除が届く。どちらでも 75 は残らない |
| 会話 A をカーソル 30 まで持つ。会話 B は未取得 | カーソルは範囲ごと | B はカーソルなしで購読し、スナップショットを受け取る |
| 三日ぶりの再接続。削除記録は保持期間を過ぎて消えている | 追いつきの条件を満たさない | スナップショット |
| DB を作り直した | 保存領域の識別子が不一致 | スナップショット。古い保存領域への未送信の操作は拒否される |
| 会話を再取り込みして項目の位置が振り直された。あるクライアントは購読中で、別のクライアントは切断中 | 履歴の置き換え | 購読中のクライアントにはスナップショットを送り直す。切断中のクライアントのカーソルは置き換えより前なので、再接続時にスナップショットを返す |
| 改名を二回した後、一回目の操作が再送される | 受付記録 | 一回目の結果を返すだけで、名前は戻らない |
| 送信が配送され、巻き戻しでその発言が消えた後、同じ送信が再送される | 受付記録は消さない | 何も起きない |
| 承認への回答の応答が失われ、クライアントが再送する | 受付記録 | 一回目の結果を返す。provider には二度送らない |
| 実行の途中でクライアントが接続する | スナップショットは最後に保存された項目を含む | その時点までの本文が出て、次の区切りから続きが届く |
| 実行中のコマンドの行を、出力が流れている途中で展開する | 出力の流れは最初に末尾の全体を送る | それまでの出力の末尾が出て、以後は追記が届く |
| 出力の流れの購読者が遅れた | 末尾の全体を送り直す | 手元の出力を置き換えて追いつく |
| 完了したコマンドの出力が大きく、行が出力を省いている | 項目の再送 | 展開したときに、本文つきの行が流れの中で届く |
| 中断して再開した後、前の試行のイベントが provider から遅れて届く | 所有者が現在の試行と比べる | 捨てる |

## 保存の形

段階 3 で作る DB の表を定める。現状の表は保存先を一つにしただけで、形は以前のままである。項目はターンの塊の中にあり、provider との対応、既読、モデル選択は全件を一つの塊で持つ(`crates/host-daemon/src/host_rpc/store.rs:82`)。

### 規則

- **一つの値は、列か本体のどちらか一方に持つ。** 列にするのは、キー、順序、SQL で絞り込む値、途中の状態の判別子だけである。それ以外は本体に持つ。本体は Rust の型をそのまま符号化したもので、状態ごとに持つ値は enum が決める。
- **同期する表の行はすべて連番を持つ。** 連番はその行を最後に変えたトランザクションのものである。
- **途中の状態は判別子の列で探せる。** 起動時に、全会話の本体を読まずに、続きが要る行を見つける。
- **Host だけが読む表を分ける。** クライアントに送る行と、provider との対応を混ぜない。
- **本体の符号化は通信と同じものを使う。** 符号化と型の定義が一つで済む。

### 表

```sql
-- 一行だけ持つ。保存領域の識別子、連番、削除記録を消し終えた連番。
CREATE TABLE store (
    id TEXT NOT NULL,
    seq INTEGER NOT NULL,
    removals_pruned_through INTEGER NOT NULL
) STRICT;

-- 同期する表
CREATE TABLE threads (
    key INTEGER PRIMARY KEY,        -- DB の中だけで使う行のキー
    provider TEXT,                  -- 会話の識別子。Bex で作った会話は provider を持たない
    id TEXT NOT NULL,
    seq INTEGER NOT NULL,
    parent INTEGER,                 -- サブエージェントの親の行のキー
    cwd TEXT,                       -- 取り込んだ会話では不明なことがある
    updated_at INTEGER NOT NULL,    -- 一覧の順
    history_seq INTEGER NOT NULL,   -- 最後に履歴を置き換えた連番
    body BLOB NOT NULL              -- 名前、今の provider、モデル選択、既読、キューの保留、一覧に出す要約
) STRICT;
CREATE UNIQUE INDEX threads_identity ON threads (ifnull(provider, ''), id);
CREATE INDEX threads_changed ON threads (seq);
CREATE INDEX threads_children ON threads (parent) WHERE parent IS NOT NULL;

CREATE TABLE projects (
    id TEXT PRIMARY KEY,
    seq INTEGER NOT NULL,
    body BLOB NOT NULL              -- 名前、フォルダ
) STRICT;
CREATE INDEX projects_changed ON projects (seq);

CREATE TABLE inputs (
    id TEXT PRIMARY KEY,            -- 操作の識別子を兼ね、配送後は発言の項目の識別子になる
    thread INTEGER NOT NULL REFERENCES threads (key) ON DELETE CASCADE,
    seq INTEGER NOT NULL,
    position INTEGER NOT NULL,      -- キューの順
    state TEXT NOT NULL,            -- preparing | queued | delivering | unknown | failed
    body BLOB NOT NULL              -- 内容、配送の種類、選んだモデル、状態ごとの値
) STRICT;
CREATE INDEX inputs_queue ON inputs (thread, position);
CREATE INDEX inputs_in_flight ON inputs (state) WHERE state IN ('preparing', 'delivering');

CREATE TABLE turns (
    id TEXT NOT NULL,
    thread INTEGER NOT NULL REFERENCES threads (key) ON DELETE CASCADE,
    seq INTEGER NOT NULL,
    ordinal INTEGER NOT NULL,       -- 使い回さない
    state TEXT NOT NULL,            -- running | waiting | completed | interrupted | failed | rolled_back
    body BLOB NOT NULL,             -- 時刻、状態ごとの値(待機中の作業、再試行の時刻、エラー)
    PRIMARY KEY (thread, id)
) STRICT;
CREATE UNIQUE INDEX turns_order ON turns (thread, ordinal);
CREATE INDEX turns_in_flight ON turns (state) WHERE state IN ('running', 'waiting');

CREATE TABLE items (
    id TEXT NOT NULL,
    thread INTEGER NOT NULL REFERENCES threads (key) ON DELETE CASCADE,
    turn_id TEXT NOT NULL,
    seq INTEGER NOT NULL,
    position INTEGER NOT NULL,      -- 会話の中での順
    body BLOB NOT NULL,             -- 種類ごとの内容。本文を含む
    PRIMARY KEY (thread, id),
    FOREIGN KEY (thread, turn_id) REFERENCES turns (thread, id) ON DELETE CASCADE
) STRICT;
CREATE UNIQUE INDEX items_order ON items (thread, position);
CREATE INDEX items_changed ON items (thread, seq);
CREATE INDEX items_turn ON items (thread, turn_id, position);

CREATE TABLE requests (
    id TEXT PRIMARY KEY,
    thread INTEGER NOT NULL REFERENCES threads (key) ON DELETE CASCADE,
    seq INTEGER NOT NULL,
    state TEXT NOT NULL,            -- awaiting | sending | unknown
    body BLOB NOT NULL              -- 対象のターンと項目、承認か質問の内容
) STRICT;
CREATE INDEX requests_thread ON requests (thread);
CREATE INDEX requests_in_flight ON requests (state) WHERE state = 'sending';

-- 同期のための表
CREATE TABLE removals (
    seq INTEGER NOT NULL,
    kind TEXT NOT NULL,             -- input | turn | item | request | project
    id TEXT NOT NULL,
    thread INTEGER,                 -- 会話の範囲の行なら、その会話の行のキー。一覧だけの行では空
    at INTEGER NOT NULL             -- 保持期間の判定に使う
) STRICT;
CREATE UNIQUE INDEX removals_identity ON removals (seq, kind, id, ifnull(thread, 0));
CREATE INDEX removals_changed ON removals (seq);
CREATE INDEX removals_thread ON removals (thread, seq) WHERE thread IS NOT NULL;

CREATE TABLE receipts (
    operation_id TEXT PRIMARY KEY,
    provider TEXT,                  -- 対象の会話の識別子。会話を消した後も残すので、行のキーでは持たない
    thread_id TEXT NOT NULL,
    seq INTEGER NOT NULL,           -- 効果を書いたトランザクションの連番
    outcome BLOB NOT NULL           -- 受付か、理由付きの拒否
) STRICT, WITHOUT ROWID;

-- Host だけが読む表

-- 会話に関わった provider のセッション。今の対応も、作り直す前のものも、取り込み元も含む。
CREATE TABLE sources (
    id INTEGER PRIMARY KEY,
    thread INTEGER NOT NULL REFERENCES threads (key) ON DELETE CASCADE,
    provider TEXT NOT NULL,
    native_id TEXT NOT NULL         -- provider のセッションの識別子
) STRICT;
CREATE UNIQUE INDEX sources_native ON sources (provider, native_id);

-- provider ごとに、今使うセッション。
CREATE TABLE bindings (
    thread INTEGER NOT NULL REFERENCES threads (key) ON DELETE CASCADE,
    provider TEXT NOT NULL,
    source_id INTEGER NOT NULL REFERENCES sources (id),
    covered INTEGER,                -- そのセッションが知っている最後のターンの順序番号
    state TEXT NOT NULL,            -- ready | injecting
    body BLOB NOT NULL,             -- 渡した履歴
    PRIMARY KEY (thread, provider)
) STRICT;
CREATE INDEX bindings_in_flight ON bindings (state) WHERE state = 'injecting';

-- ターンの試行と、それを実行した provider のセッション、provider のターン。
CREATE TABLE executions (
    thread INTEGER NOT NULL,
    turn_id TEXT NOT NULL,
    attempt INTEGER NOT NULL,
    source_id INTEGER NOT NULL REFERENCES sources (id),
    native_turn_id TEXT,            -- provider のターンの識別子
    PRIMARY KEY (thread, turn_id, attempt),
    FOREIGN KEY (thread, turn_id) REFERENCES turns (thread, id) ON DELETE CASCADE
) STRICT, WITHOUT ROWID;
CREATE INDEX executions_native ON executions (source_id, native_turn_id) WHERE native_turn_id IS NOT NULL;

-- 項目と provider の項目の対応。試行の中でだけ一意である。
CREATE TABLE item_natives (
    thread INTEGER NOT NULL,
    turn_id TEXT NOT NULL,
    attempt INTEGER NOT NULL,
    native_id TEXT NOT NULL,        -- provider の項目の識別子
    item_id TEXT NOT NULL,
    PRIMARY KEY (thread, turn_id, attempt, native_id),
    FOREIGN KEY (thread, item_id) REFERENCES items (thread, id) ON DELETE CASCADE,
    FOREIGN KEY (thread, turn_id, attempt) REFERENCES executions (thread, turn_id, attempt) ON DELETE CASCADE
) STRICT, WITHOUT ROWID;

-- 何度実行しても同じ結果になる副作用。必要とした変更と同じトランザクションで書く。
CREATE TABLE jobs (
    id TEXT PRIMARY KEY,
    kind TEXT NOT NULL,             -- 取り込み、タイトル生成、添付の削除、後片付け、切り離し、ほかの会話への受け渡し
    thread INTEGER,                 -- 結果を受け取る会話
    run_after INTEGER NOT NULL,     -- 次に実行してよい時刻
    attempts INTEGER NOT NULL,
    last_error TEXT,
    body BLOB NOT NULL
) STRICT;
CREATE INDEX jobs_due ON jobs (run_after);
```

### 書き込みの規則

既存のターンと項目の識別子は会話の中で一意なので、保存と同期のキーは必ず会話と組にする。新しい UUID についても同じ契約を使う。削除記録も会話が違えば同じ識別子を同じ連番で記録できる。

表の定義だけでは守れない約束を、ここに定める。どれも、書き込みのたびに成り立つ不変条件として試験する。

- 一つのトランザクションは、最初に `store.seq` を一つ進め、そのトランザクションで足した行と変えた行すべての `seq` をその値にする。
- 行を消すトランザクションと、ターンを巻き戻し済みにするトランザクションは、同じ連番の削除記録を書く。ターンに属する項目には、削除記録を書かない。クライアントは親と一緒に消す。
- 巻き戻し済みのターンとその項目は、行を残す。スナップショット、追いつき、範囲の拡張には含めない。ターンの順序番号と項目の位置は使い回さず、巻き戻しの後に作るものは続きの番号を取る。
- 受付記録は、操作の効果と同じトランザクションで書く。
- 履歴を置き換えるトランザクションは、`threads.history_seq` をその連番にする。

### provider の識別子の範囲

provider の識別子は、それを発行した範囲の中でしか一意でない。同じ会話でも、provider を切り替えたりセッションを作り直したりすると、同じ識別子が別のターンや項目を指し得る。対応付けは次の範囲で定める。

- provider のセッションの識別子は、provider の中で一意である(`sources_native`)。
- provider のターンの識別子は、セッションの中で引く(`executions_native`)。provider がターンの識別子を使い回すので、一意とはしない。複数の試行に当たったときは、項目の識別子の重なりで選ぶ。これは現状の規則(`turn_index`)を、取り込みの境界の一か所に残すものである。
- provider の項目の識別子は、試行の中で一意である(`item_natives` の主キー)。

実行中は所有者が現在の試行の対応をメモリに持つので、表を引くのは取り込みと、所有者を作り直した後だけである。

`threads` の本体にある一覧用の要約(状態、最後の発言の抜粋)は、`turns` と `items` から導ける値である。一覧の範囲が連番で同期できるように `threads` に置く。書くのは所有者だけで、元になる行と同じトランザクションで書くので、食い違わない。

会話の識別子は `threads` の一か所にだけ持つ。ほかの表は、DB の中だけで使う行のキーで会話を指す。行のキーは外に出さない。

`items` は会話の行のキーを、ターンを辿れば分かるのに自分でも持つ。会話の中の位置で引く索引に要るためである。ターンへの複合外部キーで、別の会話のターンを参照できないようにする。

`receipts` は `threads` を参照せず、会話の識別子をそのまま持つ。会話を消した後も、同じ操作の再送を止めるためである。

### 読み書きと索引

契約と経路が必要とする読み取りを挙げ、どの索引で引くかを決めた。上の定義を SQLite に読み込み、スナップショット、範囲の拡張、追いつき、削除記録、起動時の探索、provider からの振り分けの六つについて、実行計画が索引を使うことを確かめた。併せて三つの境界例を確かめた。別のセッションの同じ識別子が別の項目として引けること、項目を変えた後に追いつきがその項目を見つけること、履歴の置き換えの連番と等しいカーソルが有効なこと。データを入れた速さは測っていない。

| 読み取り | 使う索引 |
|---|---|
| スナップショット。末尾のターンを選び、そのターンの項目を読む | `turns_order` → `items_turn` |
| 範囲の拡張。新しく入るターンと、境界のターン内の項目 | `turns_order` → `items_turn` / `items_order` |
| 追いつき。会話の中で連番がカーソルより大きい項目 | `items_changed` |
| 追いつき。会話の中の削除記録 | `removals_thread` |
| 一覧の追いつき。プロジェクトの削除記録 | `removals_changed` |
| 一覧の追いつき | `threads_changed`、`projects_changed` |
| 起動時に続きが要る行 | `inputs_in_flight`、`turns_in_flight`、`requests_in_flight`、`bindings_in_flight` |
| provider のイベントを会話へ振り分ける | `sources_native` |
| 取り込みで既存のターンを見つける | `executions_native` |
| 取り込みで既存の項目を見つける | `item_natives` の主キー |
| 操作の再送 | `receipts` の主キー |
| 実行してよい仕事 | `jobs_due` |
| 会話の識別子から行を引く | `threads_identity` |
| サブエージェントの一覧 | `threads_children` |

**同じにした点**: 対象ごとに一行。項目は一件一行で、会話の中の位置に索引を持つ。受付記録は専用の表。本文は項目全体を上書きで保存する。実行中のコマンド出力は保存しない。どれも T3 Code の形である。

### T3 Code より良いと言える点、言えない点

- **言える点**: 同じ値を列と本体に重ねない。同じ事実を表す表が一つ(T3 Code は発言、項目、実行ノードの三つ)。Host だけが読む表が分かれている。途中の状態を列で探せる。
- **言えない点**: T3 Code の表は実際に動いていて、100 本のマイグレーションを経ている。この表はまだ書いていない。読み取りの速さも測っていない。
- **劣る点**: 本体は通信と同じ符号化(MessagePack)なので、`sqlite3` で開いても中身を読めない。T3 Code と OpenCode は JSON で、SQL の中で読める。符号化を一つにする利点を取り、調べるときは Host の読み取りコマンドを使う。本体は Rust の型から書き出すので、後から全行を読んで JSON で書き直せば替えられる。

### 確認が要る点

- `sources`、`bindings`、`executions`、`item_natives` の列と、provider の識別子が一意である範囲は、段階 3 の前に Codex、Claude、DeepSeek の接続の内部へ照らして確かめる。項目の識別子が試行の中で一意でない provider があれば、`item_natives` の主キーを見直す。
- 取り込み元の範囲(現状の `Segment`)は、`sources` と `executions` から導ける。どのターンがどのセッションから来たかを `executions` が持つためである。取り込みの経路を書くときに、これで足りることを確かめる。
- 会話の削除は現状の操作にない。足すときは、会話が存在しないことを購読の応答で返す(同期の契約)。
- ターンと項目の識別子が、端末のキャッシュ以外に保存されていないこと(展開した行の記憶など)を、段階 4 の前に確かめる。

## 戻せないものと手当て

後から変換すれば替えられるもの(本体の符号化、表の形、本文の区切り、保持期間)と、戻せないものを分ける。

### 捨てたら戻らないもの

| 捨てるもの | 手当て |
|---|---|
| 変更の履歴。行を上書きするので、過去の状態は残らない | 手当てしない。T3 Code も一日で消す |
| 巻き戻したターン | 消さずに、巻き戻し済みの状態で行を残す。T3 Code と同じである(`apps/server/src/orchestration-v2/CheckpointRollbackService.ts:349`)。利用者が決めた(2026-11-11)。巻き戻しを取り消す操作は作らない |
| 取り込みで写さなかった内容 | 手当てしない。本文だけを写すのは決定済みである。provider の履歴が残っている間は再取り込みで戻せる |
| 実行中のコマンド出力 | 手当てしない。Host が落ちれば、そのコマンドも止まっている |
| 長いコマンド出力の先頭 | 手当てしない。T3 Code と同じく末尾 64 KiB だけを残す。利用者が決めた(2026-11-11) |

### 切り替えたら戻りにくいもの

- **識別子**: 既存の会話の識別子は付け替えない(決定 1)。新しい会話から、provider を含めない形にする。これを守れば、ほかの切り替えは変換でやり直せる。
- **新しい形への移行(段階 3)**: 移行の前にバックアップを取り、古いファイルを残す。今の自動更新と同じ方式である(`crates/host-daemon/src/host_rpc/store/upgrade.rs:94`)。新しい版で会話を続けた後に古い版へ戻すと、その間の内容は失われる。
- **Host とクライアントの同時更新**: 通信の形が変わるので、古いクライアントは繋がらなくなる。iPhone は TestFlight の承認を挟むので、iPhone 版が使えるようになってから Host を上げる。

## 経路の対応

現状の全経路を、保存する状態と次の動作で書いた。provider への呼び出しは動作、何度実行してもよい副作用は仕事である(決定 8)。

| 経路 | 保存する状態 | 次の動作 |
|---|---|---|
| 新規会話の準備 | 入力が準備中(作業フォルダ、ワークツリー、provider の段階) | 足りない段階を一つ進めて保存 |
| 送信 | 入力が配送中 | provider に開始か steer を送り、発言にする |
| キュー | 入力がキュー、会話が保留かどうか | 実行がなく保留でなければ先頭を配送 |
| steer | 入力に steer の指定 | 実行中で provider が対応していれば送る。なければキュー |
| 中断 | ターンに中断要求 | provider に中断を送る |
| provider 切替 | 会話の provider、対応の段階 | 対応を履歴に合わせてから配送 |
| 巻き戻し | ターンを巻き戻し済みにする | 次の配送時に対応を合わせ直す |
| 分岐 | 新しい会話と写した履歴 | 巻き戻しと同じ |
| 容量超過の再試行 | ターンが待機(再試行の時刻) | 時刻まで待って続行 |
| 承認と質問 | 要求が待ち、送信中、済み | 回答を provider に送る |
| バックグラウンド作業 | ターンが待機(作業の一覧) | 次の入力を同じ実行に渡す |
| サブエージェント | 子の会話 | 親の所有者が、provider のイベントを受け渡しの仕事で子の所有者へ渡す |
| Host 更新での再起動 | 実行中のターンと更新の印 | 起動後に継続の入力を一つ入れる |
| 外部の会話の取り込み | 仕事表 | 履歴を読んで行にする |
| タイトル生成 | 仕事表 | 生成して、結果を所有者へ渡す |
| 添付の削除、ターミナルの後片付け | 仕事表 | 実行する |
| provider のセッションの切り離し | 仕事表 | 切り離す |

## 維持する契約

- 既存の操作と表示を維持する。受け入れ条件とスナップショットの期待値を実装に合わせて変えない。
- 既存の会話の識別子を変えない。
- 送信の結果が不明なとき、利用者に復元か破棄かを確認する。
- 中断、失敗、再起動の後はキューを保留し、利用者が再開する。
- 開いたときは最新の 10 ターンを表示し、過去はページングで読む。作業の詳細は展開したときに読み込む。会話を開く速さを落とさない。
- 外部で続けた会話は明示的な取り込みで現れる。取り込みはユーザーとアシスタントの本文だけを写す。
- アシスタントの本文は、実行中も区切りごとに表示が進む。コマンド出力は、展開した行で実行中も流れる。
- 別 Host の同じ会話や再接続前の結果で、新しい入力、エラー、録音状態を上書きしない。
- 承認、質問、キューの変更は、どのクライアントからでも同じ状態を見て操作できる。

## 段階

実装の順序は依存関係に従う。残る作業を main へ統合できる区切りは二つある。段階 2 から 5 は通信の形を一緒に変えるので、互換処理なしには分けられない。

2. **protocol**: 対象と状態の型、変更セット、操作、適用関数、`step`(決定 8)と再起動時の規則(決定 9)。「同期の契約」の不変条件と具体例を、実装より先に試験として書く。`step` の形と試験の書き方は PR #55 から取り込む。
3. **Host**: 「保存の形」の表、行と連番、削除記録、受付記録、変更セットの生成、会話ごとの所有者、仕事の実行役、対応の合わせ直し、絞った接続口と provider の記録を流す試験。メモリと保存済み履歴を合成する二経路をなくし、置き換わった `SessionActor`、`Conversations`、各ワークフローを削除する。
4. **core**: 複製、下書きの識別子、`Intent` の分割、端末キャッシュ。経路ごとの版番号の防御、仮キーの付け替え、送信の突き合わせを削除する。表示の投影の入力を替える。
5. **クライアント**: NSH、iOS、Android を追随させる。段階 2 から 5 をまとめて統合する。
6. **一覧の同期**(決定 13): プロジェクトを同じ DB に移し、provider の一覧を行にする仕事を置く。一覧を同じ連番で同期し、通知と Live Activity を一覧の変更の購読に替える。置き換わった一覧の読み取り、`list_revision`、更新と改名と活動の通知、core のページの突き合わせを削除する。ここで統合できる。

## 検証

- 「同期の契約」の不変条件を proptest で確かめる。期待値は契約から導き、実装の複製にしない。
  - **収束**: 任意の Host の履歴と任意のカーソルについて、追いつきを適用した結果は、同じ時点のスナップショットと範囲内で一致する。
  - **ライブ**: カーソル C の状態にライブを連番順に適用すると、各連番の時点のスナップショットと一致する。
  - **重複**: 同じ上書きや同じ変更セットを二度適用しても結果が変わらない。
  - **置き換え**: 任意の状態のクライアントにスナップショットを適用した結果は、何も持たないクライアントに適用した結果と同じである。
  - **範囲の拡張**: 拡張をライブのどの位置に挟んでも、適用した後の状態は、広がった範囲の Host の状態と一致する。
  - **コマンド出力**: 出力の流れを、追記と末尾の全体のどの並びで受け取っても、手元の出力は Host が持つ出力の末尾と一致する。
  - **操作**: 任意の操作の列に、任意の再送を任意の位置へ挟んでも、最後の状態は再送がない場合と同じである。
  - **再起動**: どの途中の状態からも、再起動時の規則の後に次の動作が決まる。
- 「同期の契約」の具体例は、一行ごとに試験にする。
- 状態遷移と境界の変更は、対象を絞った cargo-mutants で検査する。
- Host の経路は、上の経路表の一行ごとに、途中で落として再起動する試験を置く。
- provider の接続と `step` は、T3 Code の記録データを流して確かめる。期待値は記録データに付いた結果から導き、今の実装に合わせて変えない。
- 変更中は `scripts/dev-env.sh cargo nextest run --locked -p <crate>` と `scripts/dev-env.sh just complexity`、統合前に `scripts/dev-env.sh just unit-tests` を実行する。
- 完全な検証の報告には、対象コミットの Portable checks、対象コミットを含む main の Native clients、作業ツリーの状態を確認する。

## 確度と未確認事項

- この設計は組み合わせで、同じ形そのままの実装は存在しない。各決定に実例はあるが、全体としての検証は Bex での実装が最初になる。
- 「同期の契約」はこの計画で定めたもので、同じ規則の組を実装した例を読んでいない。行の版による適用と、範囲ごとのカーソルがそれに当たる。段階 2 で、契約の不変条件と具体例を先に試験として書き、実装より前に矛盾がないかを確かめる。
- 決定 8 の経路表は、Host のワークフローと PR #55 の副作用 10 種から作った。Claude の実行役(`providers/claude.rs`、約 880 行)と DeepSeek の内部を、段階 3 の前に経路表へ照らす。
- PR #55 から取り込む部品は、PR #55 の中で 3,976 件の試験に通っている(PR の記載)が、今の型へ書き直した後のものは試験されていない。取り込むたびに、元の試験も一緒に書き直して通す。
- 範囲内の項目の行をすべて持つ形は、現状(要約の項目だけ)より最初に送る行が増える。会話を開く速さを落とさないことを、段階 3 で実測して確かめる。ウィンドウを区切る項目数と容量は、その実測で決める。
- 本文を区切りごとに保存する頻度と、遅い接続の上限は測っていない。間隔は T3 Code の値(400 ミリ秒、800 ミリ秒、100 ミリ秒)を出発点にする。
- T3 Code は一か月で保持の方針が変わった。引用した位置は実装の前に最新で確認し直す。

## この計画に含めないもの

- クライアント側の重複(Host 一覧と接続の統括が三クライアントにある、NSH の単一 `State`、巨大なビュー関数)。別の計画で扱う。
- エラーの型付け。コマンドの結果の型として定義するのが自然だが、既存の全エラー経路に及ぶので分ける。
- ターミナル、共有ブラウザ、音声入力、Live Activity、ワークツリー管理、iroh の通信とペアリング。資源の所有者はそのままにし、永続化が必要なものだけ同じ DB に置く。
- T3 Code だけにある機能(チェックポイント、PR の連携、予約タスク)。
